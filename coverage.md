## Left out

| MCSB | Why |
| --- | --- |
| AM-2, AM-3 | Retired resource types and unused APIs. Closest NSM text is 2.1.2 c) 'eldre IKT-produkter fases ut', which is about purchasing; a candidate if 2.1.2 is to be measured in Azure. |
| BR-1 (geo-redundant database backup), BR-2 | Geo-redundancy protects against loss of a region. NSM 2.9.4 asks for copies separated from production and for offline copies, which it does not show. BR-2 holds the same four policies as BR-1. |
| DP-1, DP-2 | Defender plans; the same policies are counted once under 3.2.3 through LT-1. |
| DP-5 | Customer-managed keys. NSM 2.7.1 asks for a strategy; an organisation whose strategy uses platform-managed keys would be marked as deviating. |
| DP-6 (API Management named values), DP-8 (logs, Defender, firewall, private link) | Counted under other measures or not about key handling. |
| DS-6 | Its two policies are counted under 3.1.1 through PV-6. |
| IM-3, IM-4, IM-8 | Managed identities, API authentication and secrets found on machines. No NSM clause names them closely enough. |
| IM-6 for 2.6.7 | MCSB no longer carries the policies for MFA on subscription accounts. MFA for Azure is decided in Entra ID Conditional Access and is measured by the Maester pack (MP.NSM.1005). |
| IR-2, IR-3, IR-4, IR-5 | Incident contacts and alert quality. NSM 4.1 is planning and exercises, which are attested. |
| LT-2 | Same policies as LT-1. |
| LT-6 | Retention of SQL audit logs. NSM 3.2.5 b) is about storage space and 3.2.6 about tampering; neither is retention. |
| NS-2 (private link policies, anonymous blob access, MariaDB) | Private link is one way to meet 2.5.1, not something NSM asks for: a service with a firewall allow-list would be marked as deviating. Anonymous blob access is about authorisation, not network. Azure Database for MariaDB is retired. |
| NS-5 | DDoS protection. NSM mentions denial of service only as a topic for risk assessment in 2.2.7. |
| PA-1 (more than one owner; blocked and guest owners), PA-4 (guest accounts) | More than one owner is about availability. NSM does not ask for guests to be removed; a guest with a role is a deviation only by Microsoft's rule. |
| PA-2 | Its one policy, just-in-time access to management ports, is counted under 2.3.6 through NS-3. |
| PA-7 (custom RBAC roles) | Flags every custom role, which NSM does not advise against. |
| PV-2 (Kubernetes pod security, CORS, API Management platform version) | NSM 2.3.4 names operating systems, firewalls, network equipment, applications and hardware. Kubernetes workload rules need the organisation's own allow-lists; candidates once it has a Kubernetes standard. |
| PV-4 (trusted launch, guest attestation, Azure Stack HCI) | Hardware-rooted boot protection is not named in NSM 2.3.4 or 2.3.5. The application control policy for Azure Stack HCI is about servers; NSM 2.3.2 says clients. |
| PV-5 (secret findings) | Secrets on disk are not vulnerability mapping. |

NSM 2.3.2, 2.4.4, 2.6.4, 2.6.7, 2.7.3 and the governance measures have no policy here: they are measured on clients and in Entra ID by the NSM GP-IKT 2.1 [Maester pack](https://github.com/alventech/maester-pack-nsm-gp-ikt), or attested.
